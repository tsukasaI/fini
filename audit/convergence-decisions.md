### 2.2 収束している部分

正規化の中核。critical / high は 7/12 監査で 7 件(critical 1、high 6)、11/10 監査では中核コードに 1 件(B-02、Unicode の方針)だけ。

### 2.3 収束していない部分

- fan-out: 11/10 は high の #264、#265 の 2 件を直した PR(#270、#276)のレビューから needs-decision が 8 件生まれた。10/17 は約 13 PR から follow-up が 17 件。review-gate に `## Not filed` が入って以降は減ったが、`/triage` が拾い直すためゼロにならない。
- 再発領域:
  - 秘密情報のマスク: #44、#156、#179、#213、#229、#266、#291 の 7 世代。出力経路(`--diff`、`--stdin`、変更の要約)を足すたびに新しい漏れが出た
  - 不可視文字: #156、#179、#200、#213、#265、#277 から #280、#285 の約 10 件
  - exclude の意味: #32、#85、#92、#264、#273 から #275(#282 で BREAKING)
- 新規 issue の中身は大半が medium / low か「Decide …」形式の方針の問いで、バグではない。

### 2.4 増幅の仕組み

`CLAUDE.md` は秘密検出を「hint-only」と書く一方、利用者のグローバル規則 `rules/security.md` は「A security control must hold on every output path」と定める。マスクが制御として審査されるため、出力経路の追加がそのままバグになる。不可視文字は技術の問題ではなく方針の未決なので、毎回 Decide issue として出る。

利用者が最も強く非収束を感じた場面(原文): 「deide issueが連発していること」

## 3. 決定

| # | 決定 | 理由 |
|---|---|---|
| 1 | 秘密情報の検出はベストエフォートのヒント。網羅性を約束しない | 正規表現による検出は完全になり得ず、終わりのない領域になる |
| 2 | diff のマスクもベストエフォート(案 A2)。漏れは通常の bug として扱い、境界違反とはしない | 利用者の選択 |
| 3 | 決まった方針は `CLAUDE.md` の「Decided policy」節に書く。方針に一致する指摘は previously decided として `note` にする(データ損失を除く) | レビュアーが必ず読む場所に置き、方針の問い直しを止める |
| 4 | Unicode(不可視文字)と exclude の方針を凍結する | 既に #265、#277 から #280、#285、#273 から #275、#282、#287 で決定済み |
| 5 | 収束の指標: goal ごとに「その goal の PR から起票した needs-decision と bug の数 / その goal で閉じた issue の数」。3 goal 連続で 1 未満なら収束。PR 本文に `Closed: N / Filed: M` を書く。Not filed は数えないが、`/triage` が issue 化したら次の goal の分子に入れる。監査による起票は別に数える | 利用者の基準(原文): 「issue1に対して新規issueが1以下」。1 ちょうどでは残件が減らないため 1 未満とした |
| 6 | #294、#295 をマージして v0.8 をリリースする。それまで監査しない。残りの open issue はリリースを止めない。#282 と #286 の BREAKING はリリースノートに書く | 監査は毎回 10 から 30 件を起票し、指標を壊す |
| 7 | 監査はリリース前にだけ行い、medium 以上だけ起票する。low は監査レポートに残す | 利用者の選択(Q7' の a) |

## 4. 却下した案

- マスクを「秘密を検出したファイルは diff 本文を出さない」にする(案 A3): 保証が単純になり、出力経路を足しても漏れが生まれない。7 世代の issue の大半は「検出済みなのに表示経路で漏れる」型で、A2 ではこの型の bug が今後も起票される。利用者は A2 を選んだ。
- マスクを全経路で保証する制御として扱う(案 A1): 現状の非収束の原因そのもの。
- 秘密検出の機能を縮小・削除する(案 C): 利用者は採らなかった。
- 指標の分子を high 以上だけにする: low の起票の抑制が見えなくなる。

## 5. 未決事項

- `/triage` が `## Not filed` を issue 化し直す問題。対策は未決。
- review-gate への対応は、dotfiles を編集せずに済ませた。review-gate には既に「repo の CLAUDE.md に `## Quality bar` 節があれば、その表で指摘を振り分け、表の外の指摘は種類を問わず `note` にする」仕組みがある。fini の `CLAUDE.md` に Quality bar の表を追加し、Decided policy を問い直す指摘を表の外とした。グローバル側の穴は残っている。review-gate の既定の規則では、previously decided の指摘でも、種類が behavior / security / data-loss なら起票される。Quality bar を持たない repo では、同じ Decide issue の連発が起こりうる。
- 凍結した方針を見直す条件(利用者からの実害の報告など)。v0.8 リリース後に監査を再開する条件。
- 機能追加に対するガード(Claude の提案): 新しい機能や出力経路を実装する前に、その方針を「Decided policy」に 1 行書くことを条件とし、書けなければ実装前に Decide issue を 1 件だけ立てる。採否は明示されていない。

## 6. 追記: 組み込み先の決定(2026-11-22)

### 6.1 計測

AI が書いた内容のうち、fini が修正・検出する割合を測った。

- 対象: Claude Code の transcript(`~/.claude/projects`、直近 30 日)にある Write と Edit のツール入力。hook が走る前の生の内容である
- 方法: 各入力を `fini --stdin --check` に通す。Edit は old_string と比べて増えた分だけを、行の中で完結する種類に限って数えた
- 実行: 利用者が手元で実行(fini 0.7.0 を `cargo build --release` したもの)

- 拡張子ごとの修正率(Write): `.toml` は 14 回中 7 回、`.txt` は 124 回中 6 回、`.md` は 1,019 回中 6 回。`.rs`、`.ts`、`.json` は 0
- 検出の多くは、TODO や秘密の検出そのものを扱う fini の文書とテストによる誤検知と推測される(推測。中身は確認していない)

### 6.2 決定

- 主な組み込み先は、各リポジトリの pre-commit とする。編集ごとの Claude Code hook(PostToolUse)は主な使い方にしない。根拠は 6.1 の数値で、約 6,000 回の起動のうち意味があったのは 22 回だった
- グローバルの git フックは、当面は用意しない(利用者の判断)
- README の Claude Code hook の節は、任意の使い方として残す。編集ごとに起動するコストを注記する
- README では、pre-commit に `fini`(修正)と `fini-check`(検出でコミットを止める)を並べる構成を推奨する。修正モードは検出だけでは失敗しない仕様(#41)は変えない
- `.pre-commit-hooks.yaml` は `language: system` のままにする。`rev` で固定できるのはフックの定義だけで、実際に動くのは PATH 上の fini であることを README に明記する
- 行末の空白、EOF の改行、改行コードの修正は、出現が少なくても fini の中核として残す。利用者の言葉(原文): 「最後の改行やtrail spaceとかは確実に消したいのでそれはプログラムの役目かなと思います。決定的にできるので」
